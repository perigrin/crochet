# v0.4: Superpowers and PAAD Integration

**Due:** 2026-04-15
**Design spec:** docs/plans/2026-03-28-superpowers-paad-integration-design.md

## Context

Crochet currently treats superpowers and paad as optional peer plugins with no
formal integration. Skills hardcode references to specific paad skills
(paad:alignment, paad:agentic-architecture, paad:agentic-review) without
checking whether they are installed. This works when both plugins are present
but fails silently or produces confusing instructions when they are absent.

This milestone implements the superpowers and paad integration design. The core
change: crochet detects which superpowers and paad skills are available via a
machine-local capabilities manifest, delegates to those skills when present,
and falls back to simpler inline behavior when absent. Crochet never
reimplements what superpowers or paad already provides.

The SDLC pipeline gains a new gate (chain-review) between refinement and
execute. Two existing user-facing skills (pushback and alignment) become
internal skills called only by chain-review. The pipeline becomes:

```
superpowers:brainstorming
  -> crochet:assess (+ paad:pushback if available)
    -> crochet:refinement
      -> crochet:chain-review
        -> crochet:execute
          -> crochet:postmortem
```

## Design Rationale

### Why a capabilities manifest instead of runtime-only detection

Runtime detection (checking the system-reminder skill list) works but is
fragile — it depends on prompt formatting that could change. A manifest file
provides a stable, inspectable record of what is available. Preflight
cross-checks the manifest against runtime state on every invocation, so the
manifest self-heals if plugins are installed or removed between sessions.

### Why chain-review as a separate gate

Alignment and pushback serve complementary but distinct purposes against the
same artifact (the chain). Running them as a coordinated gate between
refinement and execute means: (a) both analyses see the complete chain before
any issue is executed, (b) they can run in parallel when
dispatching-parallel-agents is available, and (c) the user gets a single
pass/fail decision point rather than two separate invocations.

### Why pushback and alignment become internal

These skills currently have broad multi-context interfaces (pushback handles
PRD, historian, and report contexts; alignment handles refinement, historian,
tracker, and chain contexts). The design narrows each to a single focused lens:
pushback becomes the plan quality lens, alignment becomes the coverage lens.
The PRD quality checks move to crochet:assess (via paad:pushback).
Pipeline-readiness checks move to crochet:refinement. The historian and tracker
contexts are deferred — they are not part of the forward pipeline and can be
re-added as separate skills if needed.

### Why conditional references instead of hard dependencies

Crochet must work standalone. Users who install superpowers and paad get deeper
analysis (parallel dispatch, systematic debugging, structured TDD). Users
without them get simpler inline behavior that still produces correct results.
The conditional reference pattern (if available: delegate; otherwise: inline
fallback) makes this explicit in every skill file.

### Why preflight is separate from verify

Preflight runs automatically before every crochet skill — it must be fast and
silent when everything is fine. Verify is thorough and on-demand — it checks
templates, plugins, milestones, labels, and data command output. Combining
them would make every skill invocation slow, or make the on-demand check
shallow.
